# AI 協作工具的寫稿流程

用 AI 協作工具寫導讀、短訊或導讀歷史時，照本檔的做法控制 token 用量。用量多半花在兩處，一是主對話一再重讀越來越長的上下文，二是審稿每一輪重讀規則與原文的固定成本。主對話指負責寫稿的那一段對話。工具沒有子代理（subagent）時，另開一段新的對話查資料或審稿，只把清單或要改的條目貼回寫稿的對話。

## 開工前估成本

選題時先看查證的難度，記在編輯台項目的「查證難度」欄位。下面幾種題目要查證的句子多，審稿輪數也多，預設放每週短訊，維護者指定時才寫成導讀：

- 只有單方的宣稱，沒有官方說明或獨立驗證，例如外流的影片、廠商的行銷說法
- 原文有付費牆，內容要靠其他報導轉述
- 導讀觀點要比較兩個以上地方的法規，而 `notes/` 還沒有查證過的筆記

2026-10 寫 anoni-net/news#98 那篇時三種情況都碰上了，用量見「2026-10 的估算」。

## 資料蒐集的子代理

主對話不直接讀原文，因為留在對話裡的內容，之後每一回合都要重新處理一次。另外派一個子代理讀原文、各方的文件與說明頁，把頁面原樣存成純文字，放在 `/tmp/news-<slug>/` 這類暫存目錄。副本要直接抓取網頁再轉成純文字，不要存 AI 工具讀網頁之後回傳的摘要。

子代理把事實清單寫成同一個目錄的 `facts.md`，每一條編號（`F1`、`F2`），寫出事實、照錄的原文句子、網址、發布日期與頁面大標題。回傳給主對話的只有目錄路徑、事實條數與查不到的項目，不貼整份清單。

副本用指令直接存成檔案，不先讀進子代理的對話，要讀的段落用搜尋找出來再讀。讀進對話的頁面每一回合都要重讀，2026-10 底的資料蒐集一篇常到 60 到 110 回合，上下文長到 30 萬 token。工具呼叫以 40 次左右為上限，`facts.md` 邊查邊寫，查到上限還缺的項目寫成查不到，由主對話決定要不要補查。查不到的項目是給主對話與審稿判斷用的，寫稿時照 `guides/posts.md`「查證過程與內文」處理，多數不寫進內文。

主對話派資料蒐集時，一併給暫定的主線，以及想從這則新聞帶出的技術或開源專案。資料蒐集照這個角度，另外查相關的開源專案與替代工具的現況，寫進 `facts.md`。本站寫過的相關導讀也在 `posts/` 搜尋後一併列出。寫稿只能用 `facts.md` 的事實，資料蒐集沒有查，導讀觀點就寫不出社群的角度。

導讀歷史的事件在週規劃時就選好，寫在編輯台的 `導讀歷史 YYYY-Www 選題` 項目。資料蒐集只查證那一件事與現況，不再搜尋候選。編輯台上沒有選好的，主對話先決定事件再派資料蒐集。

導讀歷史的資料蒐集除了日期與法條，也要蒐集那個年代的畫面，例如當時的報導、檔案、研究或官方展示裡的具體描述、規模的數字、當時的人怎麼說（照錄短句）。查不到畫面的事件，回報給主對話換題，見 `guides/history.md`「選題」。

zh-CN 與 en 的區域段落要用的事實也在這一步查，寫在 `facts.md` 的「區域」一節。`notes/` 已經有的直接引用筆記，沒有的照一般事實的格式記下來源與日期。翻譯的子代理只用這一節與 `notes/`，不另外查資料，譯稿就不會出現沒有審過的新來源。

審稿查核事實時對照這些副本，照錄的句子與來源標題仍要到原始頁面核對，寫稿的人交稿後刪除副本。

## 寫稿與翻譯的子代理

zh-TW 的初稿也交給子代理寫，給它題目、`/tmp/news-<slug>/` 目錄、預定的檔名與時段，以及維護者已經決定的事。它讀 `guides/posts.md`（短訊與導讀歷史讀對應的那份），寫成稿與 `map.md`，照「送審前自查」改完，用 `tools/ready_check.py` 檢查，回傳成稿路徑與自己判斷不了的地方。審稿的意見交回同一個子代理修改，它還記得寫稿時的取捨。

寫稿的子代理只用 `facts.md` 與 `notes/` 的事實，但 `facts.md` 是素材，不必全部用上。先寫主線，再挑出接得回主線的事實，做法見 `guides/posts.md`「主線與取捨」。

導讀不設字數上限，但初稿交出去之前先對照篇幅。2026-10 底到 11 月初的導讀多在 1,500 到 2,100 字、14 到 16 段，讀起來像逐條轉述文件，這個範圍不是目標。初稿超過 1,500 字時，先檢查主線、查證過程與導讀觀點引入的新文件，拿掉接不回主線的段落再送審。2026-11-01 有一篇初稿約 2,460 字、19 段，第一輪審完才縮，縮稿又讓第二輪多出幾條補回前提的意見。取捨要在送審前做完。

zh-TW 審完之後寫另外兩個版本。zh-CN 主要是照 zh-TW 轉成簡體字與中國用語，再加上區域段落，用次一級的模型。en 要改寫成英文讀者讀得順的句子，用能力最高的模型。兩個版本的區域段落只用 `facts.md` 的「區域」一節與 `notes/`，事實不夠時回報缺什麼，由資料蒐集補查。新的區域事實由翻譯的子代理照 `notes/README.md` 寫進筆記，跟稿件放在同一個 PR。

翻譯交稿前另外檢查七件事。2026-11-01 的三份稿件，翻譯的子代理在前五處一再出錯，每一處都多花一輪來回。後兩處是 2026-11-21 的試寫加上的：

- 區域段落是一段，內容多時最多兩段，每段不超過 4 句。導讀的 zh-CN 與 en 都曾經寫成 5 段
- 區域段落放在導讀觀點裡、結尾那段之前，不要把同一組設定或同一件事的說明切開，也不要排在結尾之後，讓全文停在區域的事實上
- `watch` 只寫在 zh-TW，zh-CN 與 en 寫了 `build.py --check` 會失敗
- zh-TW 的 `sources` 全部保留，簡體頁、英文頁與區域段落的來源另外加上去，不要替換
- 內文不留寫給編輯的說明，例如「沒有核對簡體版的設定名稱」，要交代的寫在回報裡
- 區域段落照 `guides/posts.md`「查證過程與內文」，不寫查詢的方式與哪份文件沒寫什麼，推論寫出前提。zh-TW 審過的稿件沒有查證過程，區域段落是新寫的，最容易把它帶回來。SimpleX 那篇的 zh-CN 與 en 都寫了「iTunes API 的查詢結果，不是 Apple 的公告」，信用卡紀錄的推論也少了「由當地金融機構處理」的前提，第一輪審稿才拿掉
- 篇幅超過時，不自行刪掉 zh-TW 寫出的事實，先在回報寫明超過多少、打算刪哪幾句，由主對話決定。區域段落與照 zh-TW 翻譯的段落要一起算，超過的多半是區域段落寫太長。2026-11-21 的導讀歷史 12/15，zh-CN 為了壓回約 350 字，刪掉憲法訴願、通勤的題目與「普查員不在自家附近執勤」三項，最後一項是全文最有畫面的一句，主對話發現後才補回

## 事實對照表

寫完 zh-TW 之後，在同一個目錄寫 `map.md`。第一行寫主線，接著逐段列出每一句對應的事實編號。對不到編號的句子標成「推論」或「通則」，推論在內文用句子交代依據，寫法見 `guides/posts.md`「推論的寫法」。最後列出沒有用到的事實編號，以及沒有寫進內文的查證過程（查不到的項目、打不開的頁面），審稿看得出哪些是刻意不寫。審稿用這張表核對事實，只有照錄的句子需要核對時才開副本，不必把整個副本目錄讀一遍。zh-CN 與 en 的對照表只列跟 zh-TW 不同的句子，例如區域比較那一段。

## 送審前自查

`tools/prose_check.py` 列出有四個以上逗號分句的中文句子，以及超過句數上限的段落。句數上限在導讀與短訊是 4 句，導讀歷史是 5 句。英文只檢查段落句數，長句要靠審稿逐句讀。中文的稿件另外列出轉述感的七項：括號的推論標籤、「本文」超過兩次、交代資料缺口的句子超過兩句、連續三段用「依」或「根據」開頭、zh-TW 的導讀超過 1,500 字、連同括號超過 80 字的句子，以及寫出處或轉述的括號。後兩項是 2026-11 的導讀歷史加上的，句數上限固定時，出處容易塞進括號，括號裡的逗號又不算分句，長句檢查抓不到。逐處判斷，該拆的拆完再送審，照錄的原文標題這類不該改的可以留著。篇幅超過時寫出留下來的理由，回報給主對話。

2026-10 的審稿一再抓到下面幾類問題，送審前逐項自查，第一輪的條目就能少掉大半：

- 每一句事實都要對得到出處。同一段出自同一份文件時，段首交代一次就夠，寫法見 `guides/posts.md`「用字」。轉述的轉述寫出兩層，例如「依 9to5Mac 引述 404 Media 的內容」，同一段都來自這則轉述時，段首寫一次就夠
- 不比原文肯定。原文寫 may、likely、claims 的照樣保留，當事人的宣稱寫成某人說，報導的框架不寫進當事人的話裡
- 推論在句子裡交代依據，讓讀者看得出是推論，不加「（本文的推論）」這類括號。來源沒寫的行動建議，寫出是從哪份說明推出來的，也寫出來源沒說能不能解決問題
- 名詞先定義再使用，縮寫與專有名詞第一次出現時補一句白話
- 法規寫出全名、適用範圍與版本，草案標明是草案，不替制定機關推測修改的原因
- 會變的狀態寫出查證日期，`description` 也一樣
- 拆句、調序或刪段之後，回頭看主詞與前指有沒有消失，原文的限制與出處的歸屬有沒有一起被刪掉
- 把每一句念出來，主詞、指涉與因果的連接詞要寫出來，不要寫成資料欄位接在一起的句子，寫法見 `guides/posts.md`「資料拼接句」。為了通過長句檢查而刪掉主詞與連接詞，是最常見的成因
- 寫作風格規範裡 linter 抓不到、要自己判斷的幾條：
    - 服務、伺服器、文件不做人的動作，例如「伺服器只看得到」、「服務猜出」
    - 表示能不能做到的「V 得 + 結果」改用「能」、「可以」，例如「用得到」、「看得到」
    - 「買了的人」、「拿功能做什麼」一類的口語
    - 評語接冒號的鋪墊句，以及先下判斷、句號收尾再解釋的「結論。說明」

上面幾項都在補上缺的東西。2026-10 起的稿件只做這一組，篇幅一路變長，讀起來像逐條轉述文件。下面這組要拿掉的項目也要逐項自查，規則見 `guides/posts.md`「主線與取捨」。主線與導讀觀點兩項只適用於導讀，其餘四項短訊與導讀歷史也適用：

- `map.md` 第一行寫了主線，每一段都接得回去
- 段落依讀者的疑問排，沒有連續好幾段各從一份文件開頭
- 查證過程沒有寫進內文，例如查不到、頁面打不開、說明頁還沒更新。例外的一兩句寫成讀者用得上的事實
- 導讀觀點用前面的事實解釋原理，引入的新文件多數只有一兩份
- 「本文」一篇不超過兩次，沒有「（本文的推論）」這類括號
- 數字、日期、版本與頁面名稱只留讀者判斷用得到的
- 每次改稿，不論改動多小，都重看整篇的段落數、每段句數、摘要與觀點的比例，以及前後有沒有重複。2026-09-28 連續幾次小改之後，觀點的篇幅比摘要多出六成

## 三個語系的審稿順序

`guides/posts.md`「三個語系」一節的順序是先完成 zh-TW 的事實查核，審稿沿用這個順序，zh-TW 審完才寫 zh-CN 與 en。這兩個版本的摘要段與照 zh-TW 翻譯的段落只對照 zh-TW，不再對照原文，各自的區域段落另外照全文審。短訊與導讀歷史的 zh-CN 與 en 只審跟 zh-TW 不同的部分，例如導讀歷史第二段寫現況的句子。

## 審稿的輪數

導讀最多審三輪：

1. 第一輪審全文，給成稿、`facts.md`、`map.md` 與副本目錄，審稿讀寫作規則全文
2. 第一輪的意見改完之後派模擬讀者，回報跟第二輪的材料一起交回寫稿
3. 第二輪只送改動的段落與前後各一句，附上第一輪的意見清單、模擬讀者的回報與改了什麼。只給相關事實的副本摘錄，不給整個目錄，寫作規則改看「送審前自查」的清單
4. 第三輪讀全文收尾，材料同第二輪。第二輪只剩取捨性的意見時就不做第三輪

三輪與翻譯都審完、主對話也改完之後，開 PR 前另外做一次寫作風格的收尾，見下一節。

第二輪起只收會讓讀者誤解或違反規則的問題，措辭偏好列為取捨性的意見，寫稿的人不必採用，採用了也不再為它多審一輪。第三輪還有要改的條目時，改完只核對改動的那幾句。維護者已經決定的事，例如指定的時段，送審時寫明，審稿不再提。短訊與導讀歷史照同樣的做法，第二輪就收尾。

審稿要求補上限定條件或前提之前，先判斷那一句需不需要留著。整句拿掉也是合格的改法，審稿可以直接建議刪除。第二輪起，因為縮稿而要補回前提的意見，先問讀者需不需要那個前提。查證過程寫進內文、導讀觀點接著整理新文件、段落依文件排列，都屬於違反規則。審稿要列出這幾類，不算措辭偏好。

每篇導讀在第一輪的意見改完之後，另外派一位模擬讀者，只給成稿、不給原文與事實清單。模擬讀者照 `guides/posts.md`「各方的考量」寫的問題，檢查成稿有沒有偏向某一方，以及讀起來像不像在轉述文件。原本只派給有立場分歧的稿件，2026-11 改成每篇都派，因為轉述感最重的多半是工具與產品稿，審稿讀過事實清單，比較看不出來。模擬讀者只讀一份成稿、用次一級的模型，每篇多一次讀稿的成本。派的時間點放在第一輪之後，是因為它提的多半是標題定調、段落順序這類結構問題。2026-11-21 的試寫在第三輪之前才派，結構改完全文重寫一次，又多審一輪。

## 寫作風格的收尾

寫作風格分三層檢查。`docs_style_lint.py`（`ready_check` 與 CI）只抓詞表上的句型與口語詞，擬人化、「V 得 + 結果」、「結論。說明」這類要判斷的規則抓不到。第一輪審稿讀寫作規則全文，第二輪、第三輪與翻譯的第一輪照規定只看「送審前自查」。模擬讀者回報之後的改寫、主對話直接改的句子，以及翻譯新寫的區域段落，都落在第一輪之後。這些句子沒有人再對照規則全文。2026-11-21 的試寫通過全部的檢查，定稿仍留著「只看得到」、「服務猜出」、「買了的人」、「用得到的是」這幾句。

所以三輪審完、翻譯審完、主對話也改完之後，開 PR 前派 `news-rereviewer` 做一次寫作風格的收尾。導讀、短訊與導讀歷史都要做，同一天的稿件可以一起送。給它三個語系的成稿路徑，說明這是寫作風格的收尾。它讀寫作風格規範全文，zh-TW 與 zh-CN 照中文規範，en 照英文規範。收尾只列寫作風格的問題，不再看事實與結構。收尾列出的句子由主對話直接改，改完執行 `ready_check`，不再送審。主對話之後若又改了句子，改動的那幾句再交給同一個收尾的子代理看一次。

## 審稿的回報

回報只列要改的條目，每一條一行，寫位置、問題與建議改法，不附核對過程、已通過的項目與摘要。沒有要改的條目時，寫明只剩取捨性的意見，並列出最多三條，每條一行。

## 主對話

主對話只負責調度：決定題目與時段、派子代理、讀定稿、判斷立場與界線、開 PR。查資料、寫稿、翻譯與審稿都交給子代理。

- 對話從本 repo 的主 clone 或它的 worktree 開，不從上層的工作區或其他 repo 開。從別處開的對話讀不到 `.claude/agents/`，派出的子代理又會繼承那裡自動載入的規則與說明，見「2026-11-01 的量測」
- 一個發布日開一段新的對話，同一天的導讀、導讀歷史與短訊寫在一起，改稿留在同一段。換到下一個發布日或別的工作就重開，要延續的事寫在 repo、`notes/` 與編輯台，不靠對話的記憶。上下文要接近工具的上限才會自動壓縮，沿用同一段對話時，每一回合都要重讀幾十萬 token
- 開 PR 前執行 `uv run tools/ready_check.py <zh-TW 的路徑>`，prose_check、寫作風格、front matter 與 `build.py --check` 一次執行完，只看沒通過的項目
- 定稿的 zh-TW 全文只讀一次，zh-CN 與 en 讀審稿的回報就好
- 改稿用編輯工具改句子，不在對話裡貼整篇稿件，要確認時只讀改動的段落
- 審稿只剩一兩句要改時，主對話直接改，不再交回寫稿或翻譯的子代理。子代理每接一次都要重讀它累積的二十幾萬 token。主對話直接改的句子也要經過「寫作風格的收尾」
- 子代理的回報照上一節的格式，主對話讀過就改，不轉貼
- 查證過的區域法規與服務現況寫進 `notes/`（見 `guides/posts.md`「三個語系」），之後的稿件直接引用

## 分派多段對話

維護者用 Claude Code 的 `create_session` 把每日執行分派出去時，一個發布日一段對話，照下面的做法：

- 一段一段執行，前一段結束再派下一段。2026-11 中旬一段寫完一天的兩篇導讀與一則導讀歷史約 26 到 35 美元，四段同時執行，半小時就用完 5 小時的用量上限
- 週六那一段的指示寫明「寫當週的每週短訊」。規則把短訊交給當天的對話決定，2026-11 有兩週因此漏寫
- 子對話被權限檢查擋下時，先讀它的對話紀錄（`~/.claude/projects/` 底下的 jsonl）裡被擋前後執行的指令，跟同一個流程沒被擋的對話比對，再回報原因，不要拿推測當結論。tool_result 那一行的 `permissionDecision.reasonType` 記著放行的方式，`subcommandResults` 是允許規則放行，`classifier` 是分類器放行
- 被擋過的動作不要在同一段對話裡換一種寫法重試。2026-11-15 有一段上傳被擋之後重試兩次，兩次都被判定為規避監督

## git 與 shell 的習慣

下面每一條都出過事：

- 開 worktree 前先 `git fetch origin main`，起點寫 `origin/main`，本機的 `main` 常落後幾十個 commit
- 不用不帶參數的 `git stash`。stash 由所有 worktree 與對話共用，要暫存的修改先做成一個 WIP commit
- 串接檢查與 commit 時先 `set -o pipefail`，否則 `pytest | tail -1 && git commit` 在測試失敗時照樣 commit
- 背景的等待迴圈一律包 `timeout`，換做法時用 PID 收掉原本的迴圈。2026-10-16 有六個等待迴圈空轉了 18 小時
- 子代理回報裡要寫進稿件、PR 或 commit 的引用，落地前自己對照副本或原始頁面

## 跟維護者的協作

方向談定、下一步明確的工作直接做完再回報，不在每個階段停下來問要不要繼續。需要停下來等維護者決定的情況有三種：立場分歧的題目、正式主機的寫入或刪除、有兩種以上合理的做法。工作的範圍比原本談的大時，在回報裡另外標出來。

對話與 PR 內文用精確的名稱，例如腳本名、路徑與設定檔，不用比喻或自創的簡稱。

## 合併

維護者同意合併之後，CI 一通過就合併那一個 PR，不要累積一批一起合。分支保護要求合併前跟 `main` 同步，每合併一個，其他開著的 PR 都要再更新分支、等一次約 4 分鐘的 CI。

已經累積了好幾個時，開一段新的短對話，只帶 PR 編號清單，執行 `tools/merge_prs.sh <PR 編號> ...`。腳本依序更新分支、等 CI、squash 合併，只在有衝突或 CI 失敗時停下來，回報停在哪一個 PR。不要在寫稿的長對話裡等 CI，每次醒來都要重讀整段上下文。

2026-11-22 在寫稿的對話裡一次合併 14 個 PR，有 9 個卡在三份共用清單的衝突，花了約一個小時，用掉的額度比寫完一整天三篇稿子還多。之後預覽卡片與網站圖示改成一頁或一個主機一個檔案，網址合約改由短訊的 PR 更新（anoni-net/news#280），稿件的 PR 之間就不會再改到同一個檔案。

## 模型的選擇

派審稿與子代理時要明確指定模型。zh-TW 的第一輪審稿要逐句對照原文，才抓得到寫得比原文更肯定、把限制條件的適用範圍寫錯這類細節，所以選同一家服務裡能力最高的模型。寫 zh-TW 初稿與 en 也用能力最高的模型。zh-CN 與 en 的事實都來自審過的 zh-TW、`facts.md` 與 `notes/`，第一輪審稿選次一級的模型。

zh-CN 的翻譯、第二輪、第三輪、模擬讀者與資料蒐集的子代理，選次一級的模型就夠。用 Anthropic 的 Claude 時，能力最高的是 Opus、次一級是 Sonnet，模型改版後照同樣的分級對應。用 Claude Code 時，`.claude/agents/` 有對應這些角色的七個 agent，模型已經設好（見 `CLAUDE.md`）。
